Deployment

Deploy Suave applications to production with various hosting strategies. The examples use an application called MyApp; replace MyApp.dll with your own assembly.

Building for Production

Prepare your Suave application for production deployment:

# Framework-dependent publish (needs the .NET 10 runtime on the host)
dotnet publish -c Release -o ./publish

# Self-contained publish (no runtime needed on the host)
dotnet publish -c Release -o ./publish \
  --self-contained true \
  -r linux-x64

Suave is a self-hosted server built on sockets; it does not use ASP.NET Core, so the plain .NET runtime is enough to run it.

Configuring the Application

Suave does not read any environment variables itself: ASPNETCORE_URLS, ASPNETCORE_HTTP_PORTS and ASPNETCORE_ENVIRONMENT have no effect, and defaultConfig listens on 127.0.0.1:8080. In a container or on a machine reached directly from the network, bind to 0.0.0.0 explicitly. A common pattern is to read your own variables, such as SUAVE_IP, SUAVE_PORT and APP_ENV below:

open System
open System.IO
open System.Net.Http
open System.Runtime.InteropServices
open System.Threading
open Suave
open Suave.Filters
open Suave.Operators
open Suave.Successful

let env name fallback =
  match Environment.GetEnvironmentVariable name with
  | null | "" -> fallback
  | v -> v

let ip = env "SUAVE_IP" "127.0.0.1"
let port = int (env "SUAVE_PORT" "8080")
let isDevelopment = env "APP_ENV" "Production" = "Development"

let app =
  choose [
    path "/health" >=> OK "ok"
    path "/" >=> OK "Hello World"
  ]

/// Used by the Docker HEALTHCHECK: `dotnet MyApp.dll --healthcheck`
let healthCheck () =
  use client = new HttpClient(Timeout = TimeSpan.FromSeconds 3.)
  try
    let response = client.GetAsync(sprintf "http://127.0.0.1:%d/health" port).Result
    if response.IsSuccessStatusCode then 0 else 1
  with _ -> 1

[<EntryPoint>]
let main argv =
  if argv = [| "--healthcheck" |] then healthCheck () else

  // Stop gracefully on SIGTERM (docker stop, systemctl stop, Kubernetes)
  use cts = new CancellationTokenSource()
  use sigterm =
    PosixSignalRegistration.Create(PosixSignal.SIGTERM, fun ctx ->
      ctx.Cancel <- true // let main return instead of exiting immediately
      cts.Cancel())

  let config =
    { defaultConfig with
        bindings = [ HttpBinding.createSimple HTTP ip port ]
        cancellationToken = cts.Token
        // the application folder is often read-only (containers, non-root users)
        compressedFilesFolder = Some (Path.GetTempPath())
        errorHandler = if isDevelopment then developmentErrorHandler else defaultErrorHandler }

  startWebServer config app
  0

Error details

defaultErrorHandler answers unhandled exceptions with a plain 500 Internal Server Error and never includes the exception. Use developmentErrorHandler, which returns the message and stack trace, only on your own machine. Do not enable it based on the client address: behind a reverse proxy on the same host every request comes from 127.0.0.1. To log exceptions, write your own ErrorHandler that logs and then calls defaultErrorHandler.

Graceful shutdown

When SuaveConfig.cancellationToken is cancelled, Suave stops accepting connections and waits for requests in flight to finish for up to Tcp.shutdownDrainTimeout (5 seconds by default) before closing the remaining connections; startWebServer then returns. Without the PosixSignalRegistration above, SIGTERM ends the process straight away and drops those requests. Keep the stop timeout of your supervisor above the drain timeout (Docker waits 10 seconds by default, systemd 90 seconds).

If the server cannot bind its address, because the port is already in use for instance, startWebServer throws instead of returning, so the process exits with a non-zero code and Restart=on-failure or a Docker restart policy treats it as a failure.

Docker Deployment

Suave only needs the runtime image, not aspnet. The image below runs as the non-root user that the .NET images provide ($APP_UID), and binds to 0.0.0.0 so the published port can reach it:

# Dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/runtime:10.0
WORKDIR /app
COPY --from=build /app/publish .
ENV SUAVE_IP=0.0.0.0 \
    SUAVE_PORT=8080
EXPOSE 8080
USER $APP_UID
# The runtime image has no curl or wget, so the app checks itself
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["dotnet", "MyApp.dll", "--healthcheck"]
ENTRYPOINT ["dotnet", "MyApp.dll"]

Use the exec form of ENTRYPOINT (as above) so that dotnet is PID 1 and receives SIGTERM from docker stop. Each health check starts a short-lived dotnet process; on Kubernetes, use an httpGet probe on /health instead, which needs nothing inside the image.

Docker Compose Setup

Run Suave behind nginx with Docker Compose. Only nginx publishes ports; the health check comes from the Dockerfile:

services:
  suave:
    build: .
    environment:
      SUAVE_IP: 0.0.0.0
      SUAVE_PORT: 8080
    expose:
      - "8080"
    restart: unless-stopped

  nginx:
    image: nginx:stable
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./certs:/etc/nginx/certs:ro
    depends_on:
      suave:
        condition: service_healthy

In this setup, use server suave:8080; in the nginx upstream.

Linux Systemd Service

Run Suave as a systemd service, listening on loopback behind nginx:

# /etc/systemd/system/myapp.service
[Unit]
Description=MyApp (Suave)
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/dotnet /opt/myapp/MyApp.dll
Environment=SUAVE_IP=127.0.0.1
Environment=SUAVE_PORT=8080
Restart=always
RestartSec=10
# systemctl stop sends SIGTERM; give Suave time to drain connections
KillSignal=SIGTERM
TimeoutStopSec=15

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
journalctl -u myapp -f

Nginx Reverse Proxy

Use nginx as a reverse proxy for one or more Suave instances. The map sends Connection: upgrade only for WebSocket handshakes and keeps ordinary requests on reusable upstream connections:

map $http_upgrade $connection_upgrade {
  default upgrade;
  ''      '';
}

upstream suave {
  server 127.0.0.1:8080;
  server 127.0.0.1:8081;
  server 127.0.0.1:8082;
  keepalive 32;
}

server {
  listen 80;
  server_name example.com;

  location / {
    proxy_pass http://suave;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # WebSockets and server-sent events stay open longer than the 60 s default
    proxy_read_timeout 1h;
    proxy_send_timeout 1h;
  }

  # For server-sent events, also disable response buffering
  location /events {
    proxy_pass http://suave;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;
    proxy_read_timeout 1h;
  }
}

Behind a proxy, the connection's address is the proxy's. Read the client address with ctx.clientIpTrustProxy, which uses X-Real-IP / X-Forwarded-For, and only when Suave is reachable from the proxy alone; for rate limiting use RateLimit.trustedProxyKeyExtractor. See Rate limiting.

IIS Hosting

The ASP.NET Core Module (AspNetCoreModuleV2) is meant for ASP.NET Core applications: in-process hosting needs the ASP.NET Core server, and Microsoft documents out-of-process hosting only for Kestrel. Do not use it for Suave. On Windows, either run Suave as a Windows service and use IIS with URL Rewrite and Application Request Routing as a reverse proxy (like the nginx setup above), or let the HttpPlatformHandler module start the process and forward requests to the port it passes in HTTP_PLATFORM_PORT:

<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <system.webServer>
    <handlers>
      <add name="httpPlatformHandler" path="*" verb="*" modules="httpPlatformHandler" resourceType="Unspecified" />
    </handlers>
    <httpPlatform processPath=".\MyApp.exe"
                  stdoutLogEnabled="true"
                  stdoutLogFile=".\logs\stdout"
                  startupTimeLimit="20">
      <environmentVariables>
        <environmentVariable name="SUAVE_IP" value="127.0.0.1" />
        <environmentVariable name="SUAVE_PORT" value="%HTTP_PLATFORM_PORT%" />
      </environmentVariables>
    </httpPlatform>
  </system.webServer>
</configuration>

dotnet publish on Windows produces MyApp.exe next to MyApp.dll. As with any reverse proxy, every request then arrives from loopback.

HTTPS/SSL Configuration

Terminating TLS in nginx or a load balancer is usually simplest. To serve HTTPS from Suave directly, load the certificate with X509CertificateLoader (the X509Certificate2 file constructors are obsolete since .NET 9):

open System
open System.Security.Cryptography.X509Certificates
open Suave
open Suave.Filters
open Suave.Operators
open Suave.Successful

let cert =
  X509CertificateLoader.LoadPkcs12FromFile(
    "/etc/myapp/server.pfx",
    Environment.GetEnvironmentVariable "CERT_PASSWORD")

let httpsConfig =
  { defaultConfig with
      bindings = [
        HttpBinding.createSimple HTTP "0.0.0.0" 80
        HttpBinding.createSimple (HTTPS cert) "0.0.0.0" 443
      ]
  }

let app =
  choose [
    path "/" >=> OK "Hello World"
  ]

[<EntryPoint>]
let main argv =
  startWebServer httpsConfig app
  0

Ports below 1024 need root or CAP_NET_BIND_SERVICE on Linux (AmbientCapabilities=CAP_NET_BIND_SERVICE in the systemd unit). To redirect HTTP to HTTPS, see the HTTPS recipe.

Load Balancing

Scale Suave with multiple instances behind nginx:

services:
  suave:
    build: .
    environment:
      SUAVE_IP: 0.0.0.0
      SUAVE_PORT: 8080
    deploy:
      replicas: 3

  nginx:
    image: nginx:stable
    ports:
      - "80:80"
    volumes:
      - ./nginx-lb.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - suave

With server suave:8080; in the upstream, nginx resolves the service name to the replicas' addresses when it starts. Sessions stored with Suave.State.CookieStateStore work across instances if they share the same serverKey; generate one key and give it to every instance.

Monitoring and Logging

Wrap the application to log each request with its status and duration:

open System.Diagnostics
open Suave
open Suave.Filters
open Suave.Operators
open Suave.Successful

let withRequestLog (app : WebPart) : WebPart =
  fun ctx ->
    async {
      let sw = Stopwatch.StartNew()
      let! result = app ctx
      let status =
        match result with
        | Some c -> c.response.status.code
        | None -> 404
      printfn "%O %s -> %d in %dms" ctx.request.method ctx.request.path status sw.ElapsedMilliseconds
      return result
    }

let app =
  choose [
    path "/" >=> OK "Hello World"
  ]

[<EntryPoint>]
let main argv =
  startWebServer defaultConfig (withRequestLog app)
  0

For structured logging, see Logging.

Performance Tuning

The defaults suit most applications. These settings are the ones that matter in production:

open Suave

let productionConfig =
  { defaultConfig with
      bindings = [ HttpBinding.createSimple HTTP "0.0.0.0" 8080 ]
      // connection objects allocated at startup; more are created on demand (default 100)
      maxOps = 1000
      // socket buffer size in bytes (default 8 KiB)
      bufferSize = 8192
      // largest request body accepted, in bytes (default 10 MB)
      maxContentLength = 10 * 1024 * 1024
      // omit the Server header
      hideHeader = true }

See Performance for measurements and further tuning.
